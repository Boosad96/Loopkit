# Billing and sponsorship operations

## Merchant setup and limits

The adapter accepts only Razorpay test key IDs. A merchant can test an order before activating the account for real collections. Live eligibility requires an approved merchant account and applicable onboarding/KYC checks for the business type. Confirm settlement bank account, business category, supported products, intended countries, taxes and fees with Razorpay before launching. A working test account alone establishes no right to collect real payments.

For a business based in India, apply for international payments through the Razorpay dashboard and check current currency, payment-method, compliance and recurring-payment eligibility for that specific account. A USD price does not establish that a foreign card or an international subscription will be accepted. Supported domestic merchant international card payments generally settle in INR. An uncompleted subscription checkout with an assigned provider reference remains reserved until the provider confirms termination. The buyer can close it from Billing before starting another mandate. The conversion and fees on the provider settlement report govern reconciliation. LoopKit stores the submitted charge currency and integer amount, and performs no FX conversion. Pricing currently accepts USD cents and INR paise. Configure an INR test price if a USD plan is unavailable. [Razorpay international payments](https://razorpay.com/docs/payments/international-payments/) · [Razorpay account activation](https://razorpay.com/docs/payments/dashboard/account-settings/activation-details/)

A separate provider can implement the PaymentProvider interface. Stripe's official guidance currently describes invite-only access for Indian businesses and additional export requirements. Recheck onboarding, recurring payments, international collection and webhooks for the actual account before shipping a Stripe adapter. [Stripe India eligibility](https://support.stripe.com/questions/stripe-accounts-are-invite-only-in-india) · [Stripe India exports](https://docs.stripe.com/india-exports)

## Private test environment

1. Apply the version-controlled database migrations in numeric order on the private staging project. Configure verified authentication and create an approved community listing to test promotional checkout.
2. In Razorpay Dashboard, select **Test Mode** and generate test API keys. Enter the ID as `RAZORPAY_KEY_ID` and the secret as `RAZORPAY_KEY_SECRET` in the deployment's server secret settings. Keep the test and future live webhook URLs, signing secrets and databases isolated.
3. Create a monthly test plan with interval 1 matching the Creator Pro price in the server catalog. Set `RAZORPAY_PRO_PLAN_ID` to its identifier. The adapter fetches and compares the plan with each new subscription. Price changes apply to new authorizations. Existing subscriptions retain their confirmed provider plan.
4. Configure a test webhook at `https://<your-staging-host>/api/billing/webhook`. Set a random, separate signing secret in Razorpay and `RAZORPAY_WEBHOOK_SECRET`. Subscribe to payment.captured, payment.failed, subscription.authenticated, subscription.activated, subscription.charged, subscription.pending, subscription.halted, subscription.paused, subscription.resumed, subscription.cancelled, subscription.completed, subscription.updated, refund.created, refund.processed and refund.failed as available on the merchant dashboard. Expose only this signed callback through any staging access gateway. Enable `BILLING_TEST_ENABLED=true` only on the private staging environment. Use a dedicated test merchant context so unrelated refund deliveries can be investigated separately.
5. Open Pricing or Promote while signed in. Complete Checkout using the provider's current test payment instructions. Verify the callback receipt and webhook in the dashboard, then check Billing history. Retry a webhook delivery and confirm the ledger contains exactly one provider payment. Capture the evidence for the owner review. Never use a real card for testing. [Checkout integration](https://razorpay.com/docs/payments/server-integration/nodejs/integration-steps/) · [Subscription integration](https://razorpay.com/docs/payments/subscriptions/integration-guide/) · [Webhook verification](https://razorpay.com/docs/webhooks/validate-test/) · [Subscription events](https://razorpay.com/docs/payments/subscriptions/subscribe-to-webhooks/)

## Lifecycle

- The server snapshots the configured catalog amount into an order at reservation time. A per-user idempotency key and database transaction guard creation. A busy provider or ambiguous timeout leaves an expiring reservation for operator reconciliation. The browser cannot supply the price or an arbitrary billing owner.
- The provider identifier is recorded before opening checkout. Verification computes an HMAC from the stored provider order/subscription ID and the returned payment ID. Checkout confirmation reports receipt status. Only a separately signed provider capture grants a paid period or confirms a slot.
- Raw webhook bytes are authenticated before JSON parsing. The event ID, SHA-256 digest, provider payment ID and refund ID each participate in deduplication. Database writes occur in one transaction. HTTP 200 acknowledges a repeated valid event without duplicating a credit. Mismatched amounts or currencies roll back and produce a retryable response for investigation.
- A subscription authorizes up to twelve monthly test cycles. A recognized captured charge extends access to the provider's current period end. Expired periods stop authorizing access on reads. Cancellation is requested at cycle end from Dashboard → Billing. A processed full refund removes the affected period; a partial refund records the amount. Configure and reconcile refunds in the provider dashboard. The application never initiates a refund transaction.
- Promotions start at 00:00 UTC from the next day through 90 days ahead. A reservation covers seven exact days. Database exclusion constraints reject overlapping ranges for the same slot. Manual renewal is a new dated reservation. Fresh captures received after a hold expired are marked for merchant review, without republishing an occupied slot. A spent campaign automatically stops rendering at its end instant. No cron job is required to stop service.
- All placements require a current approved listing. Withdrawal removes that campaign from rotation and writes an admin audit entry. Withdrawal does not issue refunds. Review disputes, delayed captures, price changes, out-of-order events, provider/API timeouts and outstanding refunds under Admin → Billing. Verify payment and entitlement records after reconciliation.
- Test placement impressions and clicks support daily per-campaign deduplication behind Cloudflare with `BILLING_EDGE_METRICS=true` and a server-only random `ANALYTICS_HASH_SECRET`. Enable only when the origin exclusively trusts Cloudflare to assign its client IP header. Each digest is scoped to a day and campaign. Raw addresses are not stored. Shared IPs undercount users and address changes can count twice. Receipt cleanup occurs on subsequent metric writes. Before enabling, review applicable consent requirements and retention settings. Views/clicks measure approximate activity and provide no traffic guarantee.

## Verification boundary

Vitest uses synthetic test-only payloads. PostgreSQL integration tests exercise a real PostgreSQL engine in PGlite. End-to-end verification with the founder's own Razorpay test account, dashboard event replay, subscription cancellation and settlement review requires merchant configuration. Signed receipts are never synthesized in the running application.
