# LoopKit Growth Engine V1

The separate `loopkit-growth` Worker serves the private dashboard at `https://growth.loopkit.site/admin/growth`, the scoped Meta Muse API, and two public utilities. It uses its own Cloudflare D1 database. Discovery can run independently of the main site release and reads eligible tool URLs from the live sitemap.

[Browser setup](#browser-setup) · [Meta Muse integration](META_MUSE.md) · [Widgets and API](DEVELOPERS.md) · [Rollback](ROLLBACK.md) · [Generated registry](tool-registry.json)

## Repository and site inventory

The registry is generated from `lib/tools.ts`. It adds search terms, tool-specific advice, use cases, and sample high-intent phrases. The runtime uses the same definitions. Terms are heuristics and carry no search-volume claims. `npm run growth:registry` refreshes the checked-in file after a catalog change.

| Tools on the site | Delivery |
| --- | --- |
| Random Team Generator, Random Spin Wheel, Discord Timestamp Generator, Community Rules Generator, Tier List Maker, Discord Emoji Resizer, Telegram Sticker Resizer, Gaming Profile Card Maker | Browser-only utility editors. All eight support tool widgets. |
| Shareable Countdown Maker, Tournament Bracket Maker, Poll Maker, Leaderboard Maker, Community Event Page Maker, Shareable Goal Tracker, Community Challenge Maker, Community Link Page Maker | Hosted project editors. Existing published countdown, poll, leaderboard, event and goal widgets use their existing share controls. |

The lookup covers all 16 catalog routes. The Event Hub is the multi-tool creation surface and attaches existing projects. The community directories, blog and accounts are site features outside the tool catalog. Discovery skips temporarily disabled or unindexed tools because the live sitemap excludes them.

The live site at `loopkit.site` already serves routes and analytics headers absent from GitHub `main` as inspected on November 26, 2026. Identify its deployed source under **Workers & Pages → loopkit → Deployments/Builds** before merging or releasing the website integration. Preserve production-only changes when applying the small website patch. If a push to `main` automatically deploys that Worker, reconcile the live source first or pause that automatic deployment before merging. Steps 1–6 concern the new Worker and leave main-site routing alone.

## Browser setup

1. **Cloudflare plan and D1.** Sign in to the account that serves `loopkit.site`. Confirm **Workers Free** in the Workers overview or billing page. Open **Storage & databases → D1 → Create database**, enter `loopkit-growth`, and copy the database ID from its overview. Copy the account ID from the Workers or account overview. The deployment workflow applies the versioned migration. [D1 setup](https://developers.cloudflare.com/d1/get-started/)
2. **Cloudflare Access.** Open **Zero Trust → Access controls → Applications → Add an application → Self-hosted**. Add the public hostname `growth.loopkit.site` with path `/admin/growth`. Cover that base path and its subpaths, including `/admin/growth/assets/*` and review/scan actions. If the UI needs explicit entries, add both `/admin/growth` and `/admin/growth/*` to the same application. Add an **Allow** policy for your owner email(s) only and use your configured identity provider or one-time PIN. Copy the application **Audience (AUD) tag** and your team URL, such as `https://my-team.cloudflareaccess.com`. Scope Access to the admin path so authenticated API clients and public tools can reach their endpoints. [Self-hosted applications](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)
3. **Workflow credentials.** In Cloudflare **My Profile → API Tokens → Create Token → Custom token**, grant **Account → Workers Scripts → Edit**, **Account → D1 → Edit**, **Zone → Zone → Read**, and **Zone → Workers Routes → Edit**. Restrict it to the target account and `loopkit.site` zone. Keep this deploy-only token out of Worker secrets. In the GitHub repo open **Settings → Environments → New environment**, call it `loopkit-growth-production`, and add these values to it.

   | Kind | Name | Value |
   | --- | --- | --- |
   | Environment variable | `CLOUDFLARE_ACCOUNT_ID` | Your account ID |
   | Environment variable | `LOOPKIT_GROWTH_D1_ID` | The new D1 database ID |
   | Environment secret | `CLOUDFLARE_API_TOKEN` | The scoped deploy token |

4. **Deploy the separate Worker.** Review the branch and make the workflow available on the repository default branch. GitHub shows **Run workflow** for manually dispatched workflows once they exist on the default branch. Open **Actions → Deploy LoopKit Growth Worker → Run workflow**, select the reviewed branch or merged commit, and run it. Watch the check, dry run, remote D1 migration and deploy. The workflow sets up `growth.loopkit.site` as a Worker custom domain and adds one `*/15 * * * *` trigger. Check **Workers & Pages → loopkit-growth → Settings** for the domain and binding, then check **Triggers → Cron Triggers** for the schedule. Automatic preview URLs and workers.dev are disabled. [GitHub manual workflows](https://docs.github.com/en/actions/managing-workflow-runs/manually-running-a-workflow) · [Cloudflare custom domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)
5. **Set application credentials.** In GitHub open [scripts/credentials.html](scripts/credentials.html), download its raw file, open it locally, and select **Generate new credentials**. Save the output in your password manager. In Cloudflare **Workers & Pages → loopkit-growth → Settings → Variables and Secrets**, add the following and deploy the settings.

   | Name | Kind | Value |
   | --- | --- | --- |
   | `ACCESS_TEAM_URL` | Text | Zero Trust team URL, without a trailing slash |
   | `ACCESS_AUD` | Text | Access application audience tag |
   | `GROWTH_API_KEYS` | Secret | The generated JSON. Meta Muse receives the separate bearer credential. |
   | `GROWTH_ANALYTICS_KEY` | Secret | Optional. Set the same generated value in both Workers when enabling the website analytics bridge. |

   The optional `STACK_EXCHANGE_KEY` raises the upstream Stack Exchange allowance. GitHub public issue search works anonymously subject to its lower quota. If needed, use `GITHUB_SEARCH_TOKEN` with public read access only. You can set `ENABLE_GITHUB=false` to disable that source. `ENABLE_RSS=true` enables the official Hacker News RSS feed. `ENABLE_BLUESKY=true` opts into public Bluesky search where the hosting region permits it. Public Bluesky search returned HTTP 403 in the development environment. Verify source health before relying on it. The credentials generator is local and makes no network requests.
6. **Verify and launch.** With a private browser window, open `https://growth.loopkit.site/admin/growth` and verify Access requires sign-in. Visit `https://growth.loopkit.site/api/growth/status` without credentials and verify it returns HTTP 401. Finish your Access sign-in, open the dashboard, and select **Run scan** for an immediate first batch. The first Cron invocation starts the engine if a manual scan has not already done so. Refresh after it finishes and check the source health and first report. Open `https://growth.loopkit.site/api/v1/discord-timestamp?unix=1735689600` to verify the public API. Follow the [Meta Muse integration](META_MUSE.md) to verify the authenticated API.

## Website widgets and analytics bridge

Deploy the main-site changes only after reconciling and testing the current production source. The website patch adds widget controls to catalog pages and a route for browser-only tools. It keeps the existing project embed route and analytics opt-in flow. Existing production GA or Cloudflare Web Analytics can stay in place. The growth dashboard reads the site's own consent-based Supabase aggregates.

1. Take the owner's normal Supabase backup. In **Supabase → SQL Editor → New query**, apply [007_growth_attribution.sql](../supabase/migrations/007_growth_attribution.sql) to a staging project that already has the preceding migrations. Verify it there before applying it to the existing production project. If production has additional migrations, reconcile the migration history and apply this add-only change in that project's established order. It grants the new ingestion and aggregate procedures to the service role only.
2. Release the reconciled main-site build with its existing OpenNext deployment configuration. On the **loopkit** Worker set `GROWTH_ANALYTICS_KEY` as a secret and set `GROWTH_ATTRIBUTION_ENABLED=true` after confirming the migration is present. Keep the existing `ANALYTICS_ENABLED=true` setting if the site already uses that opt-in flow. If consented analytics are off, review the consent copy and set up the existing [retention job](../docs/ANALYTICS.md) before enabling it. Set the same `GROWTH_ANALYTICS_KEY` secret on **loopkit-growth**. It can read only the site's fixed aggregate endpoint through this credential. Supabase credentials stay on the main site.
3. On staging, open a tool page, expand **Share or embed this tool**, copy the code, and run the widget in an iframe. Confirm attribution appears only when enabled. Verify opt-in, withdrawal and Global Privacy Control. Validate attribution and conversion measurements with genuine activity from consenting browsers. Initial production values can be zero. The dashboard updates when a new 12-hour report is generated and marks disconnected or disabled analytics explicitly.

## Operation and limits

- A scan leases D1 for 60 seconds and handles one small source/query batch per invocation. It rotates through the tools, providers and keywords over successive invocations, with the first query targeting Discord timestamps. Upstream requests have a 3.5-second timeout, one retry on transient failures, backoff, bounded pagination and response sizes, and conditional caching where supported. Searches may fetch a second page in the same batch, and queries are revisited on later scans. A scan result may legitimately contain no matching questions.
- The first 48 hours use a 48-hour lookback. Freshness increases the score, and the high-intent view shows recent matches with scores of at least 78. Subsequent lookback accepts 24–72 hours via `LOOKBACK_HOURS`. Report snapshots are generated at the first run in each UTC 00:00 and 12:00 window, typically within one Cron interval. They cover the preceding 12 hours of discovery and a rolling 48 hours of available site analytics.
- The source HTTP-request caps are HN 120, Stack Exchange 100, GitHub 60, Bluesky 60 and RSS 12 per UTC day. Set lower values with `HN_DAILY_LIMIT`, `STACK_DAILY_LIMIT`, `GITHUB_DAILY_LIMIT`, `BLUESKY_DAILY_LIMIT` or `RSS_DAILY_LIMIT`. A cap of zero disables that source's searches. A throttled source pauses until the upstream retry/reset time or the next applicable scan. The Worker resumes on the new UTC day after the daily cap resets.
- The dashboard and Meta Muse share eight manual scans per day. The public tool operations share a 1,500-request global UTC daily cap, adjustable down to zero with `PUBLIC_API_DAILY_LIMIT`. Cloudflare edge rate limits apply per IP and location. Meta Muse has 600 requests per credential and 1,200 requests across credentials per UTC day. The dashboard allows 240 authenticated page views per UTC day. The Worker has no Workers AI or paid acquisition dependency. Cloudflare Free account-wide ceilings also include requests to other Workers and can return platform-level limits sooner. If unexpected public demand approaches the account ceiling, use the zone's available rate-limiting rule or disable public operations via their daily limit. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [D1 pricing and limits](https://developers.cloudflare.com/d1/platform/pricing/)
- Discovery records, scan metadata and reports age out after 30 days. Search cache rows age out after two days. The twice-daily maintenance deletes expired records, repairs interrupted scan state and writes a snapshot. Worker logs contain failure codes and scan identifiers. They exclude question bodies, credentials and tool inputs.
- Review **Open original discussion** before using a draft. Check whether self-promotion is allowed, adapt the answer to the question, and retain the LoopKit disclosure. An approval records a review action. Posting is manual and requires your own account on the discussion platform.
- The website measures opted-in first-party browser events, with grouped landing pages, standard organic referrer categories, and the allowlisted LoopKit growth/widget UTM campaigns. A session renews after 30 minutes without tracked activity, or when a distinct supported campaign begins. Returning browsers are measured on more than one UTC date within the 48-hour window. Local widget activity and public API calls are excluded from website traffic. Existing website events recorded before attribution was enabled have no session labels for this report. These counts are directional because browser telemetry can be blocked or forged.

## Developer checks

Use Node 24. Run `npm ci`, `npm run growth:check` and `npm run growth:build`. To test with local Cloudflare bindings, run `npx wrangler d1 migrations apply DB --local --config growth/wrangler.toml`, then `npx wrangler dev --config growth/wrangler.toml --test-scheduled`. Use `.dev.vars.example` for local credentials. The default D1 UUID is a local placeholder. The deploy script rejects it for remote use.
