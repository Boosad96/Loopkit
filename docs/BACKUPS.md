# Private logical backups

The private repository includes a manually dispatched **Encrypted Supabase backup** action. It has no schedule. It runs only on the private repository's main branch when the repository variable `LOOPKIT_BACKUPS_ENABLED` is exactly `true`. Configure and test it with a disposable project first. Use a GitHub-hosted ephemeral runner. If your GitHub plan has exhausted included minutes, review billing before running.

## Browser setup

1. Install a trusted OpenPGP key manager on an owner-controlled device, for example Kleopatra. In its graphical interface create an encryption-capable certificate with a strong passphrase. Back up its **private** key and passphrase to a safe owner-controlled location. Export its armored **public** certificate and copy the fingerprint. The runner receives only the public certificate. A lost private key makes archives unrecoverable.
2. In GitHub **Settings → Environments**, create `private-backup`, restrict it to protected main and configure owner review if the plan permits it. Protect changes to backup workflows. Only grant repository write and Actions permissions to trusted people.
3. In that environment create secret `BACKUP_PUBLIC_KEY` containing the public certificate including its header and footer, and variable `BACKUP_KEY_FINGERPRINT` containing the entire hexadecimal fingerprint without spaces. Create secret `BACKUP_DATABASE_URL` from Supabase **Connect → Session pooler** using port 5432 with the database password URL-encoded and TLS configured. A test merchant key, service-role key or transaction pooler URL is unsuitable. Use server certificate validation with the provider's CA where supported by your runner configuration.
4. At **Settings → Secrets and variables → Actions → Variables**, create the repository variable `LOOPKIT_BACKUPS_ENABLED=true`. Run **Actions → Encrypted Supabase backup → Run workflow**, select main and wait for its successful conclusion. Keep DDL, migrations and role changes paused during the export. Each role, schema and data dump is a separate invocation.
5. Download the encrypted artifact within three days to access-controlled storage. Decrypt a test copy and perform a restore drill. An artifact's successful upload proves transport, not recoverability. Label backups with project identity, release SHA, timestamp, data retention policy and the encryption-key fingerprint. Purge old copies according to that policy. Set the repository variable back to false when disabling the workflow.

Plain SQL and connection diagnostics are confined to the runner's memory-backed scratch directory and removed on exit. A dataset larger than available scratch space will fail; select a suitable storage/backup service before outgrowing the limit. Only encrypted compressed dumps and SHA-256 checksums are uploaded. Provider files, environment secrets, SMTP configuration, DNS, storage object payloads, customizations on managed schemas and provider billing state require independent recovery records. [Supabase backup scope and restore instructions](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)

## Verify and restore

Use a separate empty Supabase project with compatible Postgres and extensions. Disable outbound email, webhooks, analytics and checkout during a drill. A trusted operator checks SHA256SUMS, decrypts roles, schema and data archives with the owner-held key, decompresses them on an encrypted private workstation and follows the provider's documented restore order. Do not upload a plaintext SQL dump to a website or paste private database data into a chat. Recreate the project's managed-schema customizations, including the application profile trigger on auth.users, confirm RLS and grants, and validate representative cross-table records and authorized sign-ins. Inspect app/project auth settings and reacquire provider secrets separately.

The SQL Editor cannot replay a full `psql` COPY-mode archive. For a browser-administered restore, use Supabase's managed dashboard restore on an eligible plan, after approval. For the independent logical export, authorize a trusted operator to run the official `psql` restore procedure on isolated infrastructure. The founder can initiate the recovery drill and verify its results in the browser. Rehearse on staging, record actual duration, count reconciliation and tested recovery point, then dispose of decrypted recovery files. Obtain separate authorization for a production cutoff or destructive restore.
